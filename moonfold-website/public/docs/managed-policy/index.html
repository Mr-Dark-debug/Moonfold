Managed policy

A managed policy lets an administrator configure Moonfold for every user on a machine. It sets defaults and locks for settings, and limits such as the broadest permission mode or which providers may run. The Moonfold server on the machine enforces it for every app that connects: the desktop app, a browser, or the mobile app.

Roll out a policy

  1. Write the policy as JSON, starting from the example.
  2. Run moonfold policy check policy.json. It prints what the policy will do, or what is wrong with it.
  3. Deploy the policy to each machine with your device management tool, in one of the supported places.
  4. Restart Moonfold on the machine. The server reads the policy only when it starts.
  5. Run moonfold policy show on the machine to check what the server loaded.

The desktop app includes the moonfold command; see The moonfold command.

Write a policy

{
  "schemaVersion": 1,
  "organization": "Example Corp",
  "supportUrl": "https://it.example.com/moonfold",
  "settings": {
    "defaultRuntimeMode": { "value": "approval-required", "locked": false },
    "enableAgentBrowserAccess": { "value": false, "locked": true }
  },
  "limits": {
    "maxRuntimeMode": "auto-accept-edits",
    "clients": ["desktop", "local-browser"],
    "telemetry": false
  }
}

schemaVersion and organization are required. Users see the organization's name in Settings and beside each control the policy locks, with a link to supportUrl if you set one. settings sets defaults and locks, and limits restricts what Moonfold may do.

Every user on the machine can read the policy, so do not put credentials in it.

Where the policy goes

Use one of these per machine:

OSNative policyPolicy file
macOSConfiguration profile for dev.moonfold.app/Library/Application Support/Moonfold/policy.json
WindowsGroup Policy template, or a Policy JSON value (both under HKLM\SOFTWARE\Policies\Moonfold\Moonfold)C:\Program Files\Moonfold\policy.json
Linux/etc/moonfold/policy.json

Moonfold does not merge sources. If a machine has both a native policy and a policy file, Moonfold refuses to start until you remove one.

Policy file. Copy the JSON to the path for the OS. Make it and its folder writable only by administrators.

macOS configuration profile. Add a custom settings payload for the preference domain dev.moonfold.app. The payload's keys are the policy's top-level keys (schemaVersion, organization, supportUrl, settings, limits); JSON objects become dictionaries and lists become arrays. To make the payload from a policy file you checked, run plutil -convert xml1 -o dev.moonfold.app.plist policy.json and upload the result, or run moonfold policy templates <directory> --policy policy.json to write a complete macos/moonfold.mobileconfig. Install it as a device profile, since Moonfold ignores user profiles, and deploy only one profile for this domain. A profile cannot hold null, so use a policy file if a setting's value must be null.

Windows Group Policy. Run moonfold policy templates <directory> and copy windows/moonfold.admx and windows/en-US/moonfold.adml into your PolicyDefinitions folder or central store, or import them into Intune. The policies appear under Computer Configuration > Administrative Templates > Moonfold. Set Organization whenever you set any other Moonfold policy. Locks and provider fields go in the two JSON policies, as the same objects a policy file would hold. Machines pick up a change at the next Group Policy refresh; run gpupdate /target:computer /force to apply it now, then restart Moonfold. Setting Allow Moonfold Connect, Allow webhook tasks, Allow importing browser cookies, or Allow usage data to Disabled turns that feature off. Setting any other Moonfold policy to Disabled restricts nothing, the same as Not Configured.

Windows registry value. Instead of the template, set the Policy value (REG_SZ) to the whole policy as one line of JSON, from Group Policy Preferences or an Intune script. Moonfold reads it through the Windows registry API, so it works where registry tools such as reg.exe are blocked for users. Use one or the other: Moonfold refuses to start when the key holds both a Policy value and the template's settings. In PowerShell, as an administrator:

$json = (Get-Content -Raw -Encoding UTF8 policy.json) -replace '\r?\n\s*', ''
New-Item -Path HKLM:\SOFTWARE\Policies\Moonfold\Moonfold -Force | Out-Null
Set-ItemProperty -Path HKLM:\SOFTWARE\Policies\Moonfold\Moonfold -Name Policy -Value $json -Type String

Check what the server loaded

Run moonfold policy show as the user who runs Moonfold. It prints the installed policy and its fingerprint, then says whether the running server loaded that policy or an older one. The server reads the policy only when it starts, so "Restart Moonfold to apply the installed policy" means it still enforces the old one. In Settings, users see that your organization manages the environment, and each locked control shows Managed by.

Change or remove a policy

After you deploy, change, or remove a policy, restart the Moonfold server on the machine: quit and reopen the desktop app, or run moonfold service restart for the background service. Reconnecting a phone or browser does not reload the policy.

To remove a policy, delete the file, remove the profile, set the Group Policy settings to Not Configured, or delete the registry value, then restart the server. Users get back the settings they had chosen, since Moonfold never writes policy values into them.

When Moonfold refuses to start

Moonfold refuses to start rather than run with a policy it cannot fully enforce. That includes a policy it cannot read or parse, a setting it does not know, a value of the wrong type, a key this version does not support, or a machine with both a native policy and a file. The error names where the policy came from and what is wrong.

moonfold policy check catches the same problems in a JSON file. For a profile or registry value, check the JSON before you convert it. For the Group Policy template, check a complete policy file that holds the same settings, then paste its settings and limits.providers.instances objects into the two JSON policies. A policy written for a newer version can use keys an older one cannot enforce, so upgrade Moonfold before you deploy a policy that uses them.

Settings

Each key under settings is a setting's path in the server's settings.json, such as storageCleanup.logsAfterDays. To find a path, change the setting in Moonfold and look in settings.json under ~/.moonfold/userdata.

  • "locked": false sets a default. It applies wherever the user has not chosen a value of their own, and users can change it.
  • "locked": true sets the value. Users and agents cannot change it, in Settings or in a project's settings, and Settings shows the control as managed by your organization. Removing the policy brings back the user's own value.

A few settings need care:

  • A default cannot add an entry, such as a provider instance, because users could never remove it. Lock the entry instead, or set provider fields with providers.instances.
  • A setting that can be empty, such as defaultModelSelection, is managed as a whole. You cannot manage one field inside it.
  • defaultRuntimeMode cannot be broader than maxRuntimeMode.
  • worktreeCleanup, which projects can also set, overrides the worktree rules in storageCleanup. Lock it along with those rules; Moonfold refuses a policy that locks only the rules.
  • observability cannot be managed. Its OTLP endpoints come from each user's environment variables, settings file and desktop startup input, which a policy cannot override.
  • Manage idleCompaction, not the older compactIdleThreads. A Claude instance's own idle compaction choice still wins over idleCompaction.
  • A provider instance's fields override each other, so lock providerInstances.<id> as a whole, or pin single fields with providers.instances. Moonfold refuses a lock on one field inside an instance. A whole-instance lock covers only that instance; to cover every instance of a provider, use providers.instances.

Limits

limits restricts what Moonfold may do. Leave a key out to keep Moonfold's normal behavior.

{
  "schemaVersion": 1,
  "organization": "Example Corp",
  "limits": {
    "maxRuntimeMode": "auto-accept-edits",
    "clients": ["desktop"],
    "connect": false,
    "webhookTasks": false,
    "browserCookieImport": false,
    "telemetry": false,
    "providers": {
      "allowedDrivers": ["claudeAgent", "codex"],
      "instances": {
        "claudeAgent": {
          "locked": true,
          "environment": [{ "name": "CLAUDE_CODE_USE_BEDROCK", "value": "1" }]
        }
      }
    },
    "updates": { "mode": "auto", "feedUrl": "https://updates.example.com/moonfold/" }
  }
}

Permission modes

maxRuntimeMode is the broadest permission mode any thread may use: approval-required (Supervised), auto-accept-edits, auto, or full-access. It covers threads that users start, agents start, and scheduled tasks start. A thread already above the limit cannot run another turn until someone lowers its mode; its queued messages send once that happens. New threads start at the limit when the user's default is above it.

With maxRuntimeMode set, you own each provider's launch settings: binary path, launch arguments, config home, and the environment variables set on each provider. They come from providers.instances or Moonfold's defaults, and users cannot change them, because a wrapper script, a launch flag, or a variable such as NODE_OPTIONS could otherwise turn off the provider's approvals. Pin the variables your users need, such as a gateway URL, in providers.instances.

Variables in the environment that starts Moonfold itself still reach providers, and a default binary path such as claude is looked up on that environment's PATH. The desktop app builds that environment from settings the user controls, such as their shell profile, so a user could put their own claude earlier on their PATH. Pin an absolute binaryPath in providers.instances for each provider you allow.

ACP agents' own mode menus have no effect under maxRuntimeMode, except Antigravity's, whose modes Moonfold can place under the limit. Users still choose which ACP Registry agent runs; leave acpRegistry out of allowedDrivers to stop that.

The limit decides which modes Moonfold asks the provider for. It is not a sandbox; see What a policy does not cover.

Clients and Moonfold Connect

clients lists how the server may run:

  • desktop: as the desktop app's own server.
  • local-browser: as a server only browsers on this machine reach, such as npx moonfold.
  • remote: reachable from phones and other computers over the network.

remote is the line that matters. A server reachable from the network also accepts browsers on this machine, and the two local kinds differ only in how Moonfold was started. On machines with the desktop app, keep desktop in the list, or the app cannot start.

Without remote, the server listens only on a loopback address, creates no pairing links, and signs out devices that paired earlier. It does not start with a host other than a loopback address or localhost. A background service installed before MOONFOLD_LAN existed keeps private-network access, so without remote it refuses to start. Run moonfold up --no-lan when its service.env sets no MOONFOLD_HOST, or set MOONFOLD_HOST=127.0.0.1 in service.env, then run moonfold service restart. The desktop app starts with network access and Tailscale Serve off, whatever the user chose. That also turns off Moonfold Connect. To keep other remote access but turn off Moonfold Connect alone, set "connect": false.

When it starts, the server also turns off each Tailscale Serve route, HTTPS or TCP, that forwards to it, such as one moonfold pair --tailscale set up, and leaves other routes alone. It does not start while such a route stays on, or while Tailscale's answer cannot be read; the error names the command that turns the route off. A route whose target is a name, such as localhost or another machine on the same port, also stops it, since a name can resolve to this server; change the route or Moonfold's port. If Tailscale is installed but does not answer, as on a Mac where it was never set up, the server does not start until Tailscale is set up or removed. It does start when Tailscale is not installed, not running, or logged out, since nothing forwards then; a route Tailscale kept returns when Tailscale runs again, so restart Moonfold after that.

Other capabilities

  • webhookTasks: false: scheduled tasks cannot use webhook triggers. Existing webhook tasks stay but do not run, and cannot be turned back on. Users can still edit or delete them.
  • browserCookieImport: false: users cannot import cookies from another browser into Moonfold's browser.
  • telemetry: false: the server and desktop app send no product usage data or relay connection traces. A policy cannot turn them on.

Providers

providers.allowedDrivers lists the providers that may run, by ID: codex (Codex), claudeAgent (Claude), cursor (Cursor), grok (Grok), opencode (OpenCode), antigravity (Antigravity), fx (fx), kiro (Kiro), pi (Pi), muse (Muse Code), and acpRegistry (ACP Registry). moonfold policy check rejects an ID this version does not know. Threads on other providers stay, marked unavailable, and users can still turn those providers off.

providers.instances sets fields on every instance of a provider, such as an environment variable that routes Claude through Amazon Bedrock or a base URL for a company gateway. binaryPath and launchArgs work only for providers that have those settings. With "locked": true, users cannot change the fields you set. With "locked": false, the fields fill in only what the user left empty. A codex entry that is locked, or any codex entry under maxRuntimeMode, also rules out Connect with ChatGPT, since that runtime would skip your fields. In the same way, an opencode entry like that rules out a server URL, so OpenCode starts the binary you set.

Updates

  • mode: auto keeps the normal update flow. off stops Moonfold from checking for updates, for machines that get Moonfold through device management.
  • feedUrl: Moonfold updates from your own mirror instead of GitHub: the desktop app, moonfold update, and updates started from another device. Publish only the versions you have approved, laid out as on a GitHub release. The release's update files (latest.yml, latest-mac.yml, latest-linux.yml, latest-linux-arm64.yml, and their nightly versions if you allow nightly) and the desktop installers they list go at the URL's root. The release's moonfold-* archives and SHA256SUMS go under v<version>/. A moonfold run through npx comes from npm, so pin it with your package tooling.
  • allowNightly: false: the nightly channel is unavailable.

What a policy does not cover

The policy controls what Moonfold does. Agents run through each provider's own CLI, which reads its own configuration, such as ~/.claude, and which a user can also run outside Moonfold. To restrict those CLIs, use their own managed configuration, such as Claude Code's managed settings.

On a managed Windows machine, the desktop app does not run a WSL environment. A Moonfold server a user starts inside WSL reads /etc/moonfold/policy.json in that distro, not the Windows policy. Deploy the policy file there too if your users run Moonfold in WSL.

Without remote, Moonfold does not expose the server, but a user can still forward its local port with other tools.

A user with administrator rights on the machine can edit or remove the policy. Moonfold enforces the policy in its own processes, which run as the user, so it stops users from changing managed settings in Moonfold but does not stop a user who modifies or replaces Moonfold itself. A version from before managed policy ignores it too. To control which builds can run, use your device management tool's application controls.
