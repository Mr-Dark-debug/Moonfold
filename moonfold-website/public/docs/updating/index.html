Updating Moonfold

The app you use and the server running your agents can be on different machines. When a server is behind your web or desktop app, the update button at the bottom of the sidebar and Settings → Environments offer to update it.

Update everything at once

The update button at the bottom of the sidebar updates every connected machine in one step. It updates outdated providers, then servers that are behind, then the desktop app you are using. Servers move to the version your desktop app is installing, or to your web app's version. A background service stays on its current release channel. A remote desktop app installs the latest release from its own channel. Hover the button to see what it will update.

While it runs, the button widens to show progress. It names a machine that is taking longer than usual, and offers Retry for a server that failed. Click it to see every machine. The desktop app restarts once each server has started its own restart, after a short countdown. Choose Later to keep working and restart from the update button when you are ready. A server still restarting finishes on its own, and the button keeps showing it after the desktop app restarts.

Server updates come from Moonfold's GitHub Releases. Each server checks that it can install the release before it restarts. If the release is not available to a server yet, its update fails, the server keeps running, and you can retry. The confirmation lists each machine it skips and why, such as a machine that is offline or needs a manual update. Use Settings → Environments for those.

If a desktop app restarts on its old version, Moonfold tells you the update did not apply. It does not install that version again on its own, even when another device asks. Use the update button on that machine to retry.

The confirmation counts the running threads that the restarts will interrupt, and how many can resume afterwards. See Continue threads after restarts below.

Coming from beta 1 or beta 2

The desktop app's Check for Updates in beta 1 and beta 2 never finds a newer release; it reports no update. Install 0.1.0-beta.3 or later by hand once, from the releases page or with the command-line installer. Your projects, threads and settings stay. Later releases then arrive in the app.

Switch between Stable and Beta

Stable gets tested releases. Beta gets new features first; a beta install stays on Beta until you switch. In the desktop app, change Settings → About → Update track. Moonfold installs the newest build of that track over the one you have, in the same place, so your projects, threads, settings and shortcuts stay. It shows each connected machine it will move and each one it skips, then moves them in one step. Remote servers install the latest release on the new track. Remote desktop apps reinstall on the new track. This app reinstalls last.

Until the first stable release is out, Stable has nothing to install and the switch says so.

A background service cannot move to an older release remotely. When Stable is older than its Beta, run moonfold update --channel stable --allow-downgrade on that machine.

A switch is blocked for a machine whose database already has changes the target release does not support, or when Moonfold cannot confirm that it does. The dialog says why: update a machine on its current track first when its release is too old to check, or wait until the target track includes the changes. A Mac running the desktop app must switch on that Mac.

Each machine keeps the new track even if its switch did not finish, but it moves to that track only through a switch. Update track shows how many machines still run the other track. Review opens the same dialog with fresh checks.

Before you update

Server updates restart the connection and can interrupt active agents and terminal commands. Saved threads, settings, and project files remain.

Settings → Maintenance → Continue threads after restarts is on by default. It resumes supported active threads after an update, crash, or machine restart. Changes are saved to connected environments that support this setting; update older servers first. If a supported environment was offline or has a different value, use Apply to all in Settings after it connects. Moonfold must start again on that machine; the setting does not enable automatic startup. Terminal commands may still be interrupted, and threads without saved provider resume state need a new message. A thread that finished its turn to wait on a subagent, a background task, or a command or monitor the agent said it was waiting on is woken and told that this work stopped. Other background shells and monitors, such as a dev server and its watchdog, do not wake it; the thread learns about them with your next message. A thread is not resumed while it waits for your approval, answer, or secret, or while it is archived, snoozed, or settled. After three automatic resumes in a row, the thread waits for your next message.

Updates from the previous orchestration system preserve conversation transcripts but cannot carry every kind of runtime history forward. Read Threads from older Moonfold versions before continuing an important older thread.

When versions don't match

A client and server must speak the same orchestration protocol. If they do not, the connection is refused rather than running half-upgraded:

  • An app newer than the server is blocked before connecting, with a notice telling you to update Moonfold on the machine named in the notice.
  • A server newer than your app refuses the connection with an update message.

Update the side the notice names, then reconnect.

Update a connected server

The offered action depends on how the server runs:

ActionWhat to do
Update serverKeep the client open while it installs and reconnects. Supported background services update remotely. For a desktop-hosted server, this also closes and relaunches the desktop app on the host.
Update the desktop appUpdate the desktop app on the machine running the server, then reopen it if needed.
Copy update commandRun the command on the named host to update the detected global npm install, then restart the server with your usual options.
Copy relaunch commandStop the command-line server on its host and relaunch with the copied command, keeping your usual subcommand and options. This does not update an installed moonfold command.

On the host, run:

moonfold update <client-version>

Replace <client-version> with the version shown in the notice. The command asks before restarting the background service; if you decline, run moonfold service restart when you are ready. For a server you started by hand, stop it and start it again afterwards with your usual options such as --host or --tailscale-serve.

If an update fails

Keep the client open until it reconnects or reports a failure. A failed service update can roll back to the previous version. If the update still fails:

  1. Retry the offered action once.
  2. Check that you updated the server's machine, not only the device you are using.
  3. For a command-line server, stop it and relaunch the exact version shown in the notice.

Only one server can use a Moonfold home directory at a time. If startup reports that another server owns it, stop that server before retrying, or use a separate home directory and pair with the running server.

macOS app does not reopen after an Alpha update

Updating an older Moonfold (Alpha) installation can replace it with Moonfold (Beta) without reopening the app. Open Moonfold (Beta) from Applications, or run:

open "/Applications/Moonfold (Beta).app"

If an old Dock shortcut no longer opens the app, remove it and add the Beta app from Applications again.

Windows says it is searching for Moonfold (Beta).exe

An installer before 1.0.0-beta.7 could leave only Uninstall Moonfold (Beta).exe behind when a Moonfold helper was still running, so shortcuts pointed at a missing app. Install the latest release from the releases page over it; your data stays. From beta 7 the installer closes such helpers first.

If the desktop app does not start

If the desktop app's server keeps failing at startup, Moonfold shows a "Moonfold could not start" window instead of the app. If a newer version is available, choose Update to install it. If not, the window links to the last version that started on your computer. Download and install it to go back. Use Copy details to include the error in a bug report.

Registries and proxies

Each server checks Moonfold releases, and providers installed with npm, through its own npm, so the checks use npm's configured registry, authentication, and proxy settings. Providers installed with Homebrew or pnpm check through those tools. Configure npm on the server's machine. If that registry cannot be reached, the release shows as unavailable; Moonfold does not try the public registry instead. Machines without npm check the public npm registry directly.

Update providers

Settings → Providers shows provider updates for the selected environment. Update all updates every outdated provider on every connected environment at once. Hover it to see which providers it will update. Providers that only offer a manual update command are not included.

After a successful provider CLI update, Moonfold refreshes model discovery for every enabled instance of that provider using its own configuration. Connected clients receive the refreshed catalogs automatically. Provider update checks must be enabled to download the latest Moonfold model catalog.

Provider updates do not restart running chats. An existing session can keep using the previous CLI until it ends. If discovery fails, check the provider status and refresh it again.
